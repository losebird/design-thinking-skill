# 定义视角 Define Point of View

目标：把共情阶段的大量发现收敛成**一句简洁、好记、可作为下一轮起点的问题陈述（PoV）**，并导出 HMW 问题。这是设计思维中最难的一步。
产物：洞察聚类、360 度视角、九宫格、雏菊图、JTBD 语句、PoV 句子、HMW 问题、关键假设清单。

## 1. 核心工作（洞察漏斗）
1. 回顾、解释并衡量所有发现；主持人鼓励每个人分享经历、照片、当时的反应与情绪，建立共同语言。
2. 用新洞察修订画像。
3. 收集、结构化、衡量所有洞察——找出要点，也找出矛盾，决定下一轮优先级。（→ `boards.insights` 聚类 + 投票）
4. 漏斗收敛：总结约 10 条最重要的洞察 → 推断设计原则或问题集合 → 投票选出 3 个主题 → 每个主题提出问题 → 选一个问题打磨。（→ `pov.html` 第①步）

## 2. 关键要点
- **多角度（360 度视角）**：从不同利益相关方及“金钱”“年龄”等维度看问题。（→ `radials.view360`）
- **结构化**：九宫格视窗——系统层级（子系统/系统/超系统）× 时间（过去/现在/未来）（→ `boards.ninegrid`）；雏菊图——5–8 片花瓣表示同等重要的要素，避免列表带来的默认排序（→ `radials.daisy`）。
- **把别人眼中的问题视为机会**；澄清假设与假说（→ `tables.assumptions`）；突出最核心的洞察。
- PoV 是构思阶段的直接输入。

## 3. JTBD 待完成任务（→ `define.jtbd`）
核心理念：用户不是“买”产品，而是“雇佣”它完成某个任务。经典例子：人们要的不是 1/4 英寸的钻头，而是 1/4 英寸的洞；早高峰的奶昔被“雇佣”来打发无聊的通勤、撑到中午。
- 三个维度：**功能性任务**（实际问题）、**情感性任务**（过程中的感受）、**社会性任务**（在他人眼中的形象）。
- 句式：**当 [情境] 时，我想要 [动机]，这样我就能 [预期结果/情感]。**
- 坏例子（关注产品）：“用户想要更大容量的播放器”；好例子（关注任务）：“当我在户外长跑时，我想听连贯、节奏感强的音乐，这样我能保持专注、不必停下切歌。”
- 价值：摆脱人口统计的误导；重新定义竞争对手；避免功能内卷。

## 4. PoV 句子（→ `define.pov`，`format` 取值见下）
| format | 句式 |
|---|---|
| `standard`（d.school） | [用户] 需要 [需求]，因为 [令人意外的洞察]。 |
| `story`（用户故事） | 作为一名 [用户角色]，我想要 [需求/目的]，以便于 [益处]。 |
| `storyPain`（用户故事变体） | 作为一名 [用户角色]，我希望 [需求]，但 [痛点]。 |
| `hmw` | 我们可以如何 [帮助用户] ……？ |
好 PoV 的要素：明确的用户、清晰的需求（目标）、痛点或益处、一个深刻的洞察。

### JTBD → PoV 的对齐
- JTBD 的“任务” = PoV 的“需求”（把“我要买台灯”换成“深夜阅读时不打扰室友”）。
- JTBD 的“情感/社会任务与情境” = PoV 的“洞察”（把“因为天黑”换成“怕漏光吵醒室友、破坏宿舍关系”）。
- **最常见错误：把方案写进需求**。“需要一个更亮的台灯”已经是解决方案，会把团队锁死在“改进台灯”上；“因为熄灯后太暗”是正确的废话，不是洞察。
- 模板 `pov.html` 会检测需求中的方案词（App、功能、按钮、平台……），并提醒洞察过短。

## 5. HMW 我们可以如何（→ `define.hmw`）
从 PoV 导出 3–5 个 HMW：范围不宽到无从下手，也不窄到只剩一个答案。例：“我们可以如何让光只留在书页上？”“我们可以如何让文字自己发光？”“我们可以如何让他不靠视觉也能‘读书’？”——分别引出防漏光书灯、电子墨水阅读器、有声书。给最好的 HMW 加星，作为头脑风暴题目。

## 6. 方案不是需求 —— 自查
- 需求句里出现具体产品形态、功能、技术名词？→ 改写成用户要完成的任务。
- 洞察是不是“正确的废话”？→ 追问“为什么这件事对 TA 重要？”
- 洞察有证据吗？标注来源，没有就放进关键假设清单。

## 7. 桌面研究的收敛（→ `deskResearch.synthesis`、`deskResearch.gaps`、`deskResearch.report`）
做过桌面研究时，在写 PoV 之前：用「综合矩阵」把来源整理成共识 / 分歧 / 不确定，用「研究空白」区分已知 / 未知 / 需验证（需验证项会进入「待真人验证」清单），再用「研究报告」把背景 → 发现 → 含义 → 行动建议交给团队。二手发现在洞察与 PoV 中最多算 `inferred`，不能当作用户原话或观察。详见 `desk-research.md`。

## 8. 价值主张画布（→ `value-canvas.html`，数据 `valueCanvas`）——分阶段使用
价值主张画布分两侧，**不要在同一时间填完**：

**定义阶段填：顾客档案侧（Customer Profile）**
- **Jobs**：用户要完成的功能型 / 情感型 / 社交型任务（直接来自 JTBD）
- **Pains**：完成任务时遇到的障碍、风险和负面结果
- **Gains**：用户期待的好处、惊喜、期望结果

此时**不填**解决方案侧。填了也是凭空猜测，会过早锁死方向。

**构思阶段（有方向后）补填：价值地图侧（Value Map）**
- **Products & Services**：提供的产品 / 功能列表
- **Pain Relievers**：具体缓解哪条 Pain，如何缓解
- **Gain Creators**：具体创造哪条 Gain，如何创造

契合度检查：Pain Relievers 覆盖 100% 的 Pains，Gain Creators 覆盖 ≥70% 的 Gains。没有对应 Gain 的功能是"自嗨功能"，优先砍掉。
